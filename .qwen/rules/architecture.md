# Архитектурные правила SmartSchedule

## 1. Пользователь — окончательный архитектор

Архитектор-агент помогает анализировать и проектировать систему, но не обладает полномочиями самостоятельно принимать 
окончательные архитектурные решения.

Архитектор:

- анализирует текущую архитектуру;
- предлагает варианты;
- описывает плюсы и минусы;
- выявляет последствия;
- формулирует контракты;
- фиксирует ограничения;
- готовит постановки.

Окончательное решение принимает пользователь.

---

## 2. Архитектор не должен выдавать предложение за решение

Если существует несколько вариантов, архитектор должен показать варианты и дождаться явного approval пользователя.

После approval выбранный вариант считается согласованным.

---

## 3. API-контракты

API-контракт является общей границей между backend и frontend.

Frontend и backend агенты не имеют права самостоятельно договариваться об изменении API-контракта.

Изменениями контракта считаются, в том числе:

- изменение URL;
- HTTP method;
- request body;
- response body;
- названия или типы полей;
- обязательность полей;
- коды ошибок;
- формат ошибок;
- правила авторизации;
- pagination;
- sorting;
- filtering;
- изменение семантики существующего endpoint.

Если постановка явно не предусматривает изменение существующего контракта, агент не должен изменять его самостоятельно.

При необходимости изменения:

Backend/Frontend Agent
→ Architect
→ User approval
→ обновление постановки/контракта
→ реализация.

---

## 4. База данных

Схема базы данных является архитектурным контрактом.

Без явно согласованного требования запрещено:

- создавать таблицы;
- удалять таблицы;
- добавлять столбцы;
- удалять столбцы;
- изменять типы столбцов;
- изменять nullable;
- изменять primary keys;
- изменять foreign keys;
- изменять unique constraints;
- изменять indexes;
- изменять database constraints;
- изменять существующие migration-файлы.

Если изменение БД прямо указано в согласованной постановке — оно разрешено в рамках этой постановки.

Если изменение БД не указано — остановиться и передать вопрос архитектору.

---

## 5. Backend / Frontend не принимают совместных архитектурных решений

Backend Agent и Frontend Agent могут использовать уже согласованный контракт.

Они не должны самостоятельно договариваться:

- об изменении API;
- о структуре данных;
- о новой бизнес-логике;
- о способе хранения данных;
- о новых сущностях;
- о новых архитектурных слоях.

При необходимости такого решения используется цепочка:

Agent
→ Architect
→ User, если решение не было ранее согласовано.

---

## 6. Изменение архитектуры

Если для выполнения задачи агент считает необходимым:

- добавить новый слой;
- удалить существующий слой;
- изменить ответственность существующего слоя;
- изменить способ взаимодействия модулей;
- изменить технологию;
- существенно изменить существующую структуру;

он должен остановиться и сообщить об этом архитектору.

Не выполнять архитектурное изменение самостоятельно.

---

## 7. Существующий код не является автоматически правильным

Наличие существующей реализации не означает, что её необходимо копировать или что она является архитектурным эталоном.

При этом агент не должен самостоятельно проводить масштабный рефакторинг существующего кода только потому, что 
обнаружил возможность улучшения.

Отдельные предложения по улучшению передаются архитектору/пользователю.

---

## 8. API и Controller

Для backend HTTP API используется разделение Controller и API-документации.

Для каждого Controller должен существовать соответствующий API-класс в package `api`.

Пример:

```text
controller/
    TaskController.java

api/
    TaskApi.java
```

Controller отвечает за реализацию endpoint.

API-класс отвечает за описание публичного HTTP-контракта и OpenAPI/Swagger-документацию.

API-класс не должен содержать бизнес-логику.

---

## Согласованность Controller и API

При изменении endpoint необходимо одновременно проверить:

* URL;
* HTTP method;
* request;
* response;
* параметры;
* HTTP-коды;
* ошибки;
* OpenAPI-документацию;
* примеры request/response.

Документация должна соответствовать фактической реализации.

Изменение публичного API без обновления API-документации считается незавершённой реализацией.

---

## DTO и Entity

DTO и Entity, участвующие в публичном API, должны иметь необходимую документацию полей.

Описание должно отражать фактическое назначение поля.

Изменение DTO, которое влияет на публичный API, должно сопровождаться обновлением соответствующей OpenAPI-документации.
