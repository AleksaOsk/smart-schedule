# Правила стиля кода SmartSchedule

## 1. Общий принцип

Новый код должен соответствовать согласованным соглашениям проекта.

Перед написанием нового кода агент обязан изучить существующие аналогичные классы и определить принятый в проекте стиль.

Приоритет правил:

1. явно согласованные правила проекта;
2. `checkstyle.xml`;
3. существующие аналогичные классы;
4. общепринятые Java conventions.

Если источники противоречат друг другу — не угадывать. Передать вопрос архитектору.

---

## 2. Именование Java-кода

Для Java использовать следующие правила:

* классы и интерфейсы — `PascalCase`;
* методы — `camelCase`;
* локальные переменные — `camelCase`;
* поля — `camelCase`;
* константы — `UPPER_SNAKE_CASE`;
* enum-константы — `UPPER_SNAKE_CASE`;
* package — `lowercase`.

Не использовать сокращения без необходимости.

Предпочтительно:

```text
taskRepository
scheduleService
calculateDeadline
workingDays
```

Не использовать неясные сокращения:

```text
tr
ss
calc
wd
```

Исключения допускаются для общеупотребительных сокращений и уже существующих соглашений проекта.

---

## 3. Суффиксы классов по package

Классы должны иметь суффикс, соответствующий назначению и package.

Для соответствующих package использовать:

* `dto` → `Dto`;
* `service` → `Service`;
* `repository` → `Repository`;
* `controller` → `Controller`;
* `api` → `Api`.

Примеры:

```text
TaskDto
TaskService
TaskRepository
TaskController
TaskApi
```

Если класс относится к другой специальной области, использовать существующее соглашение проекта.

Не создавать классы с неоднозначными названиями, если из package и имени невозможно определить назначение класса.

---

## 4. Не переименовывать существующий код без необходимости

Если существующее имя соответствует текущим соглашениям проекта, не переименовывать его только ради личного предпочтения.

Если обнаружено несоответствие существующего кода стилю:

* не выполнять массовый рефакторинг автоматически;
* не переименовывать несвязанные элементы;
* не исправлять старый код только ради соответствия новому правилу;
* сообщить об обнаружении архитектору или пользователю, если изменение необходимо.

Новые изменения должны соответствовать актуальным правилам проекта.

---

## 5. Методы

Названия методов должны описывать выполняемое действие или проверяемое условие.

Хорошие примеры:

```text
calculateDeadline()
findById()
createTask()
validateSchedule()
isWorkingDay()
hasAvailableTime()
```

Не использовать неопределённые названия без необходимости:

```text
process()
handle()
execute()
doSomething()
```

Название метода должно позволять понять его назначение без чтения реализации.

---

## 6. Размер методов

Метод не должен превышать 30–35 строк.

Если метод становится длиннее установленного ограничения:

1. не увеличивать допустимый лимит;
2. определить логически самостоятельные части;
3. при необходимости вынести их в отдельные методы;
4. сохранить понятность и ответственность исходного метода.

Не создавать искусственные методы только ради уменьшения количества строк.

Если соблюдение лимита требует архитектурного изменения — передать вопрос архитектору.

---

## 7. Размер классов

Класс не должен превышать 800 строк.

Если класс приближается к ограничению, не следует автоматически проводить масштабный рефакторинг.

Если превышение связано с новой задачей:

* определить причину;
* оценить возможность локального выделения ответственности;
* при необходимости передать вопрос архитектору.

---

## 8. Пустые строки

Между отдельными полями должна быть пустая строка.

Между отдельными методами должна быть пустая строка.

Логически связанные элементы могут группироваться вместе, если это соответствует существующему стилю проекта.

Не создавать чрезмерное количество пустых строк внутри логически единого блока.

Форматирование должно соответствовать `checkstyle.xml`.

---

## 9. API-документация

Для каждого Controller должен существовать соответствующий API-класс в package `api`.

Например:

```text
controller/TaskController.java
api/TaskApi.java
```

API-класс используется для описания HTTP API и отображения документации в Swagger/OpenAPI.

---

## 10. Документация API

Каждый API-метод должен иметь документацию OpenAPI.

Документация должна содержать настолько полное описание endpoint, насколько это необходимо для понимания API.

В зависимости от endpoint должны быть указаны:

* краткое описание;
* подробное описание, если необходимо;
* параметры;
* request body;
* response;
* возможные HTTP-коды;
* описание ошибок;
* примеры request;
* примеры response;
* ограничения или особенности использования, если они существуют.

Документация должна быть понятной при просмотре Swagger UI.

Цель — чтобы API можно было понять по Swagger без необходимости читать реализацию Controller.

---

## 11. DTO и Entity documentation

DTO и Entity должны содержать OpenAPI/Javadoc-документацию для публично значимых полей.

Для полей необходимо указывать понятное описание их назначения.

Если для поля важны:

* допустимые значения;
* формат;
* ограничения;
* обязательность;
* единицы измерения;
* пример значения;

эта информация должна быть отражена в документации, если соответствующая OpenAPI-аннотация это поддерживает.

Документация не должна быть формальной или бесполезной.

Плохо:

```text
"description = \"Task name\""
```

если из контекста невозможно понять ограничения или назначение.

Предпочтительно описание, объясняющее смысл поля для потребителя API.

---

## 12. Formatting

Форматирование должно соответствовать существующему `checkstyle.xml`.

Не отключать Checkstyle для обхода ошибок.

Не добавлять локальные исключения из правил только для того, чтобы код прошёл проверку.

Не изменять форматирование несвязанных файлов без необходимости.

---

## 13. Checkstyle

Checkstyle является автоматической проверкой соблюдения кодового стиля.

Coding-agent обязан после изменения backend-кода:

1. запустить Checkstyle;
2. исправить обнаруженные ошибки;
3. повторно запустить Checkstyle;
4. убедиться в успешном прохождении;
5. только после этого считать локальную проверку стиля завершённой.

Если правило Checkstyle противоречит согласованному требованию или архитектуре:

* не отключать правило самостоятельно;
* не изменять `checkstyle.xml` самостоятельно;
* передать вопрос архитектору/пользователю.

---

## 14. Изменение Checkstyle

`checkstyle.xml` является частью правил проекта.

Coding-agent не должен самостоятельно:

* отключать существующее правило;
* ослаблять существующее правило;
* добавлять исключения;
* изменять лимиты;
* заменять конфигурацию.

Изменения Checkstyle выполняются отдельно и только по согласованному решению пользователя.

---

## 15. Старый код

Существующий код не считается автоматически неправильным только потому, что он не соответствует новому правилу.

Новые изменения должны соответствовать актуальным правилам.

Массовое приведение старого кода к новому стилю выполняется только отдельной согласованной задачей.

---

## 16. Область действия

Эти правила относятся прежде всего к Java/backend-коду.

Frontend использует существующие соглашения frontend-проекта и отдельные frontend-инструменты проверки, если они определены.

Backend Agent обязан соблюдать эти правила при изменении `backend/`.
