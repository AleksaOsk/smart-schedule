# Общие правила для всех агентов SmartSchedule

## 1. Роль пользователя

Пользователь является единственным владельцем окончательных решений по:

- бизнес-логике;
- требованиям;
- архитектуре;
- API-контрактам;
- структуре базы данных;
- изменениям между frontend и backend;
- спорным техническим решениям;
- принятию или отклонению результатов code review;
- слиянию изменений в `main`.

Агенты являются исполнителями и консультантами.

Агент не должен самостоятельно принимать решение там, где требуется решение пользователя.

---

## 2. Согласованные решения

Решение считается согласованным только если пользователь явно его одобрил.

Не считать согласованным:

- собственное предположение агента;
- решение предыдущего агента;
- решение, которое кажется очевидным;
- существующую реализацию, если она противоречит текущей постановке;
- предложение, которое пользователь ещё не подтвердил.

Если решение не согласовано и оно влияет на архитектуру, контракт, БД или бизнес-логику — остановиться и запросить решение.

---

## 3. Не додумывать отсутствующие требования

Если для выполнения задачи не хватает информации:

1. проверить существующие согласованные постановки и контракты;
2. проверить правила проекта;
3. проверить существующий код;
4. если ответ найден — использовать его;
5. если ответа нет — не придумывать решение самостоятельно.

Передать вопрос архитектору.

Если архитектор не располагает согласованным решением — вопрос должен быть передан пользователю.

---

## 4. Не расширять задачу самостоятельно

Агент должен выполнять только согласованную задачу.

Не следует самостоятельно:

- добавлять функциональность "на будущее";
- проводить крупный рефакторинг;
- менять архитектуру;
- менять API;
- менять схему БД;
- исправлять несвязанные проблемы;
- менять файлы за пределами своей зоны ответственности.

Если изменение кажется необходимым — сообщить об этом через установленный процесс согласования.

---

## 5. Сохранение существующего поведения

Не изменять существующее поведение без причины и без соответствующего требования.

Если новая задача требует изменения существующего поведения, это должно быть явно отражено в согласованной постановке.

---

## 6. Работа с ошибками

Если агент обнаружил проблему, которая препятствует выполнению задачи:

- не скрывать проблему;
- не обходить её молча;
- не менять архитектуру самостоятельно;
- не создавать неподтверждённые workaround-решения.

Зафиксировать проблему и передать её по установленному процессу.

---

## 7. Коммуникация

Агенты должны формулировать вопросы конкретно.

Плохой вопрос:

"Что делать?"

Хороший вопрос:

"Для операции X возможны варианты A и B.

A:
- ...

B:
- ...

Для текущей архитектуры последствия следующие:
- ...

Требуется ваше решение: A или B."

---

## 8. Язык общения и документации

Основной язык общения с пользователем — русский.

На русском языке необходимо писать:
- сообщения и ответы пользователю;
- анализ требований и архитектуры;
- отчёты о выполненной работе;
- постановки задач в `.qwen/tasks`;
- описания задач и критерии готовности;
- документацию, которую ты создаёшь или изменяешь;
- комментарии к Pull Request и результаты ревью, если они входят в твою работу.

Английский язык допускается для:
- названий классов, методов, переменных и файлов;
- идентификаторов API и полей;
- команд Git и фрагментов кода;
- названий технологий, библиотек и общепринятых технических терминов;
- других случаев, когда перевод ухудшит точность технического описания.

Если исходная документация написана на английском, анализируй её на языке оригинала, но излагай результаты на русском.

При создании или обновлении существующих задач сохраняй все технические требования, ограничения, зависимости, критерии
готовности и согласованные решения. Не меняй смысл требований ради перевода.

Не переводи автоматически исходный код, идентификаторы, команды и значения конфигурации.

Если пользователь явно попросил использовать другой язык для конкретного результата, следуй этому указанию.
