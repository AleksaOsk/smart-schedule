# Git Rules

## 1. Общий принцип

Git является частью рабочего процесса проекта SmartSchedule.

Пользователь является владельцем репозитория и единственным лицом, принимающим окончательные решения о:

* структуре веток;
* изменениях, попадающих в `main`;
* merge;
* разрешении конфликтов;
* изменении Git workflow;
* изменении branch protection rules.

Coding-agents являются исполнителями.

Агент не должен считать собственное решение достаточным основанием для изменения Git workflow.

---

## 2. Ветка `main`

Агенты НЕ имеют права:

* писать изменения непосредственно в `main`;
* создавать commit в `main`;
* выполнять `git push` в `main`;
* выполнять merge в `main`;
* выполнять force-push в `main`;
* отключать или обходить branch protection;
* изменять правила защиты `main`.

Перед началом работы агент обязан проверить текущую ветку.

Если текущая ветка:

```text
main
```

агент не должен изменять production-код.

Сначала необходимо создать или переключиться на соответствующую task branch.

---

## 3. Task branches

Каждая задача должна выполняться в отдельной ветке.

Предпочтительный формат:

```text
feature/<task-id>-<short-description>
```

или:

```text
fix/<task-id>-<short-description>
```

Примеры:

```text
feature/BE-001-create-user-service
feature/FE-002-task-list
fix/BE-003-user-validation
```

Название ветки должно однозначно соответствовать задаче.

Не используй одну ветку для нескольких независимых задач.

---

## 4. Начало работы над задачей

Перед изменением файлов агент обязан проверить:

1. текущую Git-ветку;
2. статус рабочей директории;
3. наличие незакоммиченных изменений;
4. существование task branch;
5. соответствие текущей ветки выполняемой задаче;
6. актуальность постановки задачи.

Если в рабочей директории уже есть незакоммиченные изменения, которые не принадлежат текущей задаче:

* не удаляй их;
* не откатывай их;
* не перезаписывай их;
* не добавляй их в commit;
* остановись и сообщи пользователю.

---

## 5. Незнакомая или неправильная ветка

Если текущая ветка не соответствует задаче:

не начинай изменять код.

Сначала:

1. проверь существующие branches;
2. определи, существует ли подходящая task branch;
3. если ситуация неоднозначна — остановись и спроси пользователя.

Не создавай новую ветку поверх незавершённой работы без проверки состояния репозитория.

---

## 6. Область изменений

Каждая задача должна изменять только файлы, необходимые для её выполнения.

Запрещено добавлять в commit:

* unrelated changes;
* временные файлы;
* IDE-файлы;
* секреты;
* локальные конфигурации;
* результаты сборки;
* изменения другой задачи.

Перед commit агент обязан проверить:

```text
git status
```

и убедиться, что в commit попадут только изменения текущей задачи.

---

## 7. Backend Agent

Backend Agent работает только над согласованными backend-задачами.

По умолчанию разрешённая область:

```text
backend/
```

Backend Agent не должен самостоятельно изменять:

```text
frontend/
```

а также:

```text
.qwen/agents/
.qwen/rules/
```

без отдельного approval пользователя.

Изменения в следующих областях требуют отдельного внимания и должны быть предусмотрены постановкой задачи:

```text
.github/
backend/pom.xml
backend/checkstyle.xml
backend/src/main/resources/db/migration/
backend/src/main/resources/application.yml
```

Если изменение этих файлов не предусмотрено постановкой, агент должен остановиться и сообщить об этом.

---

## 8. Frontend Agent

Frontend Agent работает только над согласованными frontend-задачами.

По умолчанию разрешённая область:

```text
frontend/
```

Frontend Agent не должен самостоятельно изменять:

```text
backend/
```

а также:

```text
.qwen/agents/
.qwen/rules/
```

без отдельного approval пользователя.

Если frontend-задача требует изменения backend API:

* агент не должен самостоятельно изменять backend;
* необходимо проверить согласованный API-контракт;
* если контракт не предусматривает требуемое изменение — остановиться и передать вопрос Architect Agent / пользователю.

---

## 9. Architect Agent

Architect Agent не является coding-agent.

Architect Agent может работать с:

```text
.qwen/tasks/
```

для создания и обновления согласованных постановок.

Architect Agent не должен:

* изменять production backend-код;
* изменять production frontend-код;
* создавать implementation commits;
* изменять API самостоятельно;
* изменять БД самостоятельно;
* выполнять merge;
* принимать архитектурные решения вместо пользователя.

Git используется Architect Agent только в пределах согласованного workflow проекта.

---

## 10. Reviewer Agent

Reviewer Agent является read-only агентом.

Reviewer Agent может:

* читать Git diff;
* читать commit;
* читать branch;
* читать task specification;
* читать исходный код;
* анализировать тесты;
* анализировать изменения.

Reviewer Agent не должен:

* изменять файлы;
* создавать commit;
* изменять commit;
* выполнять push;
* выполнять merge;
* approve PR;
* самостоятельно исправлять найденные проблемы;
* отдавать coding-agent команды вне установленного workflow.

Reviewer Agent формирует только review report.

Решение о внесении исправлений принимает пользователь.

---

## 11. Commit

Commit должен содержать только изменения одной логически связанной задачи.

Не создавай commit, если:

* задача не завершена;
* тесты не пройдены;
* Checkstyle не пройден для backend;
* обязательные проверки не выполнены;
* имеются неизвестные ошибки;
* в commit попадут изменения другой задачи.

### Формат commit message

Каждый commit обязан начинаться с номера задачи.

Формат:

```text
<TASK-ID>: <description>
```

Примеры:

```text
BE-001: add user creation service
BE-002: validate task periodicity
FE-001: create task list
FE-002: add task creation form
```

Описание должно быть коротким и отражать фактически выполненное изменение.

Не используй:

```text
changes
fix
update
work
some changes
final
```

если сообщение не содержит номера задачи и понятного описания изменения.

Один commit должен относиться только к одной задаче.

Если в рамках одной задачи создаётся несколько commit, каждый commit должен содержать тот же `TASK-ID`.

Пример:

```text
BE-001: add user entity
BE-001: add user repository
BE-001: add user service tests
```

Не смешивай в одном commit изменения разных задач:

```text
BE-001: add user service and FE-002: create task page
```

Если изменения относятся к разным задачам, они должны находиться в отдельных branches и commits.

## 12. Push

После успешного завершения задачи агент может отправить task branch в remote repository, если это предусмотрено его 
ролью и постановкой.

Push разрешён только в task branch.

Пример:

```text
feature/BE-001-create-user-service
```

Push в:

```text
main
```

запрещён.

Force-push запрещён.

Не используй:

```text
git push --force
git push --force-with-lease
```

без явного разрешения пользователя.

---

## 13. Pull Request

Backend и Frontend agents после завершения задачи могут создать Pull Request из task branch.

PR должен содержать:

* ссылку на task ID;
* краткое описание изменений;
* список основных изменений;
* информацию о тестах;
* информацию о Checkstyle для backend;
* известные ограничения или проблемы;
* информацию о необходимости дополнительных решений, если они есть.

PR не должен объединять независимые задачи.

---

## 14. Merge

Агенты никогда не выполняют merge.

Merge выполняет только пользователь.

Даже если:

* тесты проходят;
* Reviewer не нашёл проблем;
* CI зелёный;
* PR готов;
* GitHub разрешает merge;

агент всё равно не должен самостоятельно выполнять merge.

Финальное решение о merge принадлежит пользователю.

---

## 15. Reviewer после PR

После создания или обновления PR может быть выполнен Reviewer Agent.

Reviewer проверяет:

1. соответствие постановке;
2. соответствие архитектуре;
3. соответствие code style;
4. соответствие API-контракту;
5. корректность тестов;
6. потенциальные edge cases;
7. отсутствие unrelated changes;
8. наличие необходимых API/OpenAPI documentation;
9. отсутствие очевидных регрессий.

Reviewer не изменяет код.

После review:

```text
REVIEW
   ↓
проблем нет
   ↓
пользователь рассматривает PR
```

или:

```text
REVIEW
   ↓
есть замечания
   ↓
пользователь решает, какие изменения нужны
   ↓
coding-agent исправляет
   ↓
тесты
   ↓
новый review
```

---

## 16. Изменения после review

Reviewer не имеет права самостоятельно передавать coding-agent команду на исправление.

Пользователь принимает решение:

* принять замечание;
* отклонить замечание;
* запросить дополнительный анализ;
* изменить постановку;
* создать отдельную задачу.

Если исправление требует изменения архитектуры, API или БД, необходимо вернуться к Architect Agent и получить решение пользователя.

---

## 17. Конфликты

Если возник merge conflict:

агент не должен самостоятельно принимать архитектурное решение о разрешении конфликта. Передай решение пользователю.

---

## 18. Параллельные задачи

Несколько агентов могут работать параллельно только при отсутствии конфликтующих областей.

Перед автоматическим переходом к следующей задаче агент должен убедиться:

1. предыдущая задача завершена;
2. тесты проходят;
3. Checkstyle проходит для backend;
4. commit создан;
5. нет незакрытых блокеров;
6. следующая задача уже согласована Architect Agent и пользователем;
7. зависимости следующей задачи выполнены;
8. области изменения задач не пересекаются;
9. следующая задача не требует нового архитектурного решения;
10. API и DB-контракты уже определены.

Особое внимание необходимо уделять общим файлам:

```text
pom.xml
package.json
application.yml
configuration files
database migrations
API contracts
shared types
tests
CI configuration
```

Даже если две задачи относятся к разным функциональным областям, изменение одного общего файла может создавать конфликт.

Если области пересекаются, автоматический переход к следующей задаче запрещён без дополнительного решения.

---

## 19. Новая задача должна иметь новую ветку

При переходе к следующей независимой задаче нельзя продолжать работу в branch предыдущей задачи.

Например:

```text
feature/BE-001-user-service
```

после завершения не превращается в:

```text
feature/BE-001-user-service + BE-002-task-service
```

Вместо этого создаётся:

```text
feature/BE-002-task-service
```

Каждая задача должна иметь собственную историю изменений.

---

## 20. Изменение Git workflow

Агентам запрещено самостоятельно изменять:

* branch protection;
* repository rules;
* merge strategy;
* required approvals;
* required status checks;
* GitHub Actions permissions;
* repository permissions;
* access control;
* правила обхода защиты `main`.

Такие изменения выполняет только пользователь после отдельного решения.

---

## 21. Секреты

Никогда не добавляй в Git:

* passwords;
* API keys;
* access tokens;
* private keys;
* JWT secrets;
* database credentials;
* `.env` с реальными секретами;
* другие credentials.

Перед commit проверь изменения на наличие случайно добавленных секретов.

Если секрет был обнаружен в уже созданном commit:

не пытайся самостоятельно скрыть проблему переписыванием Git history.

Сообщи пользователю.

---

## 22. Отмена изменений

Агент не должен выполнять destructive Git operations без необходимости.

Без явного разрешения пользователя запрещены операции, которые могут удалить незакоммиченные изменения:

```text
git reset --hard
git clean -fd
git checkout -- <file>
git restore <file>
```

Не удаляй изменения пользователя для того, чтобы сделать рабочую директорию чистой.

---

## 23. Незакоммиченные изменения пользователя

Если до начала работы обнаружены изменения, происхождение которых агент не может уверенно определить:

не изменяй и не удаляй их.

Сообщи:

* какие файлы изменены;
* какие изменения обнаружены;
* почему невозможно безопасно определить их принадлежность.

Дальнейшее действие определяет пользователь.

---

## 24. Проверка перед завершением задачи

Перед объявлением задачи готовой агент должен проверить:

### Git

* правильная task branch;
* нет случайных изменений;
* нет секретов;
* commit содержит только изменения задачи;
* push выполнен только в task branch.

### Backend

Если задача backend:

* тесты проходят;
* Checkstyle проходит;
* не отключены или ослаблены правила Checkstyle;
* нет unrelated изменений.

### Frontend

Если задача frontend:

* проект собирается;
* предусмотренные lint/format/test проверки проходят;
* нет unrelated изменений.

### Workflow

* задача соответствует approved specification;
* API соответствует согласованному контракту;
* DB изменения соответствуют постановке;
* архитектурные решения не были приняты самостоятельно;
* все необходимые блокеры явно указаны.

---

## 25. Приоритет правил

При конфликте Git-правил используй следующий порядок:

1. явное решение пользователя;
2. branch protection и технические ограничения репозитория;
3. approved task specification;
4. `.qwen/rules/git.md`;
5. остальные `.qwen/rules`;
6. общие Git conventions.

Если конфликт нельзя однозначно разрешить — не угадывай. Остановись и обратись к пользователю.

---

## 26. Основной workflow

Стандартный workflow задачи:

```text
APPROVED TASK
      ↓
CHECK CURRENT BRANCH
      ↓
CHECK WORKING TREE
      ↓
CREATE / SWITCH TO TASK BRANCH
      ↓
IMPLEMENT
      ↓
RUN TESTS
      ↓
RUN CHECKSTYLE / LINT
      ↓
REVIEW LOCAL CHANGES
      ↓
COMMIT
      ↓
PUSH TASK BRANCH
      ↓
CREATE / UPDATE PR
      ↓
REVIEWER
      ↓
USER DECISION
      ↓
FIXES IF REQUIRED
      ↓
FINAL USER REVIEW
      ↓
USER MERGES
      ↓
MAIN
```

Агент не должен пропускать этапы workflow без явного основания и соответствующего правила.

---

## 27. Главный принцип безопасности

Если действие может:

* изменить `main`;
* удалить чужие изменения;
* потерять незакоммиченные изменения;
* изменить архитектуру;
* изменить API;
* изменить БД;
* обойти branch protection;
* изменить Git workflow;
* скрыть проблему в истории Git;

не выполняй его самостоятельно.

Остановись и передай решение пользователю.
