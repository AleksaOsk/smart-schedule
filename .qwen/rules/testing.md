# Правила тестирования SmartSchedule

## 1. Тесты являются обязательной частью разработки

При изменении production-кода агент должен определить необходимые тесты и добавить или изменить их.

Тесты должны проверять:

- основной сценарий;
- ожидаемые ошибки;
- граничные случаи;
- важные бизнес-правила;
- изменённое поведение.

---

## 2. Покрытие

Целевое покрытие нового или изменённого кода — не менее 90%.

Не следует искусственно добавлять бессмысленные тесты только ради увеличения процента coverage.

Тест должен проверять поведение, а не просто выполнять код.

---

## 3. Тесты должны проходить до Reviewer

Последовательность:

1. Реализация.
2. Добавление/изменение тестов.
3. Запуск тестов.
4. Исправление найденных проблем.
5. Повторный запуск.
6. Проверка coverage.
7. Только после успешного прохождения тестов — передача Reviewer Agent.

Если тесты падают, задача не считается готовой для Reviewer.

---

## 4. Ошибки тестов

Если тест падает из-за ошибки собственного кода агента — агент должен самостоятельно попытаться исправить её.

Если причина требует архитектурного решения, изменения API или изменения БД — остановиться и передать вопрос по 
установленному процессу.

---

## 5. Не изменять тесты только ради зелёного CI

Запрещено:

- удалять падающие тесты без причины;
- ослаблять assertions без обоснования;
- отключать тесты;
- менять expected result только для получения green build;
- скрывать ошибку.

Изменение существующего теста должно соответствовать изменению требований или поведения системы.

---

## 6. CI

Локально пройденные тесты не заменяют CI.

После создания PR агент должен учитывать результаты CI.

Если CI обнаружил проблему, агент должен разобраться с ней в своей ветке.

Если исправление требует архитектурного решения — передать вопрос по установленному процессу.
