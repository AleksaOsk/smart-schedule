# Рабочий процесс SmartSchedule

## 1. Общий жизненный цикл задачи

Задача проходит следующие состояния:

DRAFT
→ PLANNED
→ APPROVED
→ IN_PROGRESS
→ IMPLEMENTED
→ REVIEW
→ CHANGES_REQUESTED
→ REVIEW
→ APPROVED
→ MERGED

Не все задачи обязаны проходить абсолютно все состояния, но нельзя пропускать обязательное пользовательское согласование.

---

## 2. DRAFT

Пользователь формулирует идею или требование.

Архитектор анализирует её.

---

## 3. PLANNED

Архитектор:

- анализирует существующий проект;
- выявляет зависимости;
- определяет необходимые изменения;
- формулирует варианты;
- выявляет вопросы;
- предлагает архитектурное решение;
- определяет API-контракт;
- определяет изменения БД, если они необходимы;
- предлагает декомпозицию.

---

## 4. APPROVED

Пользователь проверяет предложенное решение.

Только после явного approval архитектор может считать решение согласованным.

---

## 5. Постановка

После согласования архитектор создаёт или изменяет файл постановки.

Постановка должна содержать достаточно информации для самостоятельной работы соответствующего coding-agent.

Рекомендуемая структура:

- ID задачи;
- цель;
- контекст;
- требования;
- ограничения;
- API-контракт;
- изменения БД;
- критерии готовности;
- тестовые требования;
- зависимости.

---

## 6. Декомпозиция

Архитектор делит согласованную работу на небольшие независимые задачи.

Каждая задача должна иметь:

- конкретную цель;
- понятный результат;
- владельца: Backend или Frontend;
- зависимости;
- необходимые контракты;
- критерии готовности.

Не создавать огромные задачи, охватывающие всю систему без необходимости.

---

## 7. IN_PROGRESS

Coding-agent получает конкретную согласованную задачу.

Перед началом он должен:

1. прочитать постановку;
2. проверить зависимости;
3. проверить согласованные контракты;
4. проверить свою рабочую директорию;
5. проверить Git branch;
6. убедиться, что задача понятна.

---

## 8. Недостаток информации

Если данных недостаточно:

Agent
→ Architect

Если Architect не имеет согласованного ответа:

Architect
→ User

Agent не должен самостоятельно продолжать спорное место.

---

## 9. IMPLEMENTED

Задача считается реализованной только после:

- выполнения требований;
- добавления необходимых тестов;
- прохождения тестов;
- проверки coverage;
- отсутствия известных блокирующих проблем.

---

## 10. REVIEW

Только после успешного прохождения тестов задача передаётся Reviewer Agent.

Reviewer анализирует:

- постановку;
- diff;
- изменённый код;
- тесты;
- потенциальные ошибки;
- соответствие ограничениям.

---

## 11. CHANGES_REQUESTED

Reviewer не распоряжается разработчиком.

Пользователь читает результат анализа Reviewer и самостоятельно решает:

- ничего не менять;
- попросить изменить код;
- задать дополнительный вопрос;
- изменить постановку;
- передать вопрос архитектору.

Если пользователь решил внести изменение, соответствующий coding-agent выполняет его.

---

## 12. Финальное approval

После исправлений пользователь самостоятельно проводит настоящее code review.

Только пользователь принимает решение о merge.

---

## 13. Merge

Только пользователь может выполнить merge PR в `main`.
