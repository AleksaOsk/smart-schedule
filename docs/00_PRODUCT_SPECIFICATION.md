# SmartSchedule — Product Specification

## Ключевая идея

SmartSchedule — трекер повторяющихся задач и автоматический планировщик рабочего времени.

Продукт автоматически рассчитывает экземпляры повторяющихся задач, учитывает рабочие дни, доступную ёмкость, 
DAY/NIGHT-ограничения и правила переноса, а при неразрешимом конфликте передаёт выбор пользователю.

## Зафиксировано

### Порядок задач
```text
DAY_TO_DAY
→ DAY_BEFORE
→ DAY_BEFORE_OR_AFTER
→ NO
```

### Перенос
- `DAY_TO_DAY`: только target date.
- `DAY_BEFORE`: target date или предыдущий день. Никогда позже.
- `DAY_BEFORE_OR_AFTER`: предыдущий, target или следующий день.
- `NO`: неограниченный перенос с поиском ближайшего допустимого дня.

### `NO` при равной дистанции
Если две даты равноудалены и обе подходят:
1. ищет ближайший день до или после;
2. если дни равноудалены, то выбирается день с большим количеством уже занятых часов, если задача помещается;
3. если занятое время одинаково — день раньше.

То же правило предпочтения дня раньше применяется к равноудалённым вариантам `DAY_BEFORE_OR_AFTER` (пп 2-3).

### Время суток
- `DAY` — только день.
- `NIGHT` — только ночь.
- `DAY_AND_NIGHT` — время суток не важно; это не означает одновременное выполнение в двух сменах.

### Конфликты
- первый найденный неразрешимый конфликт останавливает генерацию;
- пользователь видит конфликтующие задачи;
- пользователь сам выбирает, какую задачу переносить;
- пользователь выбирает дату или относительный перенос;
- Backend валидирует решение;
- решение может создать следующий конфликт;
- предыдущая успешная генерация не затрагивается.

### Генерация
```text
STARTED
→ GENERATING
→ WAITING_FOR_USER
→ GENERATING
→ COMPLETED
```
Состояние хранится в БД. Одновременно у пользователя только одна активная генерация.

### Хранение
Хранится только последняя успешная генерация. Она сохраняется до успешного результата следующей генерации и удаляется 
не позднее чем через 2 месяца.

### Повторяющиеся задачи
Следующая дата считается от последнего фактического выполнения. Пропущенные периоды не backfill'ятся: периодичность 
прибавляется, пока не получена актуальная дата для периода генерации.

### Даты конца месяца
Используется стандартная Java date arithmetic (`plusMonths`, `plusYears` и тд).

### Перерыв
В automatic work-time mode отдых просто вычитается из доступной рабочей ёмкости.

## OPEN QUESTIONS

1. Первый execution date новой задачи, созданной в середине периода.
2. Формальная модель смены пользователя на конкретную дату и противоречие в трактовке одновременных DAY/NIGHT задач.
3. Может ли `DAY_AND_NIGHT` быть разбита на несколько сегментов.
4. Конечная граница генерации «с выбранной даты».
5. Несколько рабочих интервалов в одном дне.
6. Формат Conflict API.
7. Retry и manual resend email.
8. Message broker или scheduler/outbox.
9. Supabase Auth + Spring Security.
10. RLS и admin model.
