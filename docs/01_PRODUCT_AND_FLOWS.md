# 2. Цели проекта

SmartSchedule должен:

* хранить повторяющиеся задачи пользователя;
* учитывать рабочие и выходные дни;
* учитывать продолжительность рабочего дня;
* учитывать дневные и ночные рабочие интервалы;
* автоматически распределять задачи по доступному времени;
* учитывать периодичность выполнения задач;
* учитывать длительность задач;
* учитывать ограничения на перенос задач;
* учитывать порядок приоритета задач при построении расписания;
* обнаруживать конфликты;
* при обнаружении конфликта приостанавливать генерацию;
* запрашивать решение пользователя;
* продолжать генерацию после решения конфликта;
* позволять пользователю начать генерацию заново;
* формировать готовое расписание;
* отображать расписание пользователю;
* отправлять сформированное расписание на email;
* отправлять расписание в удобном для пользователя формате;
* хранить только последнюю завершённую генерацию расписания;
* удалять предыдущую завершённую генерацию после создания новой;
* автоматически удалять сохранённое расписание не позднее чем через 2 месяца.

# 3. Пользователь

Пользователь работает только со своими данными, задачами и расписанием.

Пользователь должен иметь возможность:

* зарегистрироваться;
* войти в систему;
* выйти из системы;
* просматривать свой профиль;
* создавать задачи;
* редактировать задачи;
* удалять задачи;
* настраивать рабочие дни;
* настраивать рабочее время;
* настраивать дневные и ночные рабочие интервалы;
* выбирать режим рабочего расписания;
* запускать генерацию расписания;
* разрешать конфликты;
* отменять текущую генерацию;
* начинать генерацию заново;
* просматривать сгенерированное расписание;
* получать расписание на email;
* удалить свой аккаунт вместе со всеми связанными данными.

# 4. Основной пользовательский сценарий

Общий сценарий работы:

```text
Регистрация / вход
        ↓
Настройка рабочего расписания
        ↓
Создание повторяющихся задач
        ↓
Запуск генерации
        ↓
Подтверждение фактических дат выполнения
        ↓
Анализ задач и доступного времени
        ↓
Построение расписания
        ↓
┌─────────────────────┐
│ Есть конфликт?      │
└──────────┬──────────┘
           │
       ┌───┴───┐
       │       │
      Нет     Да
       │       │
       │       ▼
       │   WAITING_FOR_USER
       │       │
       │       ▼
       │   Пользователь
       │   решает конфликт
       │       │
       └───┬───┘
           ▼
     Продолжение генерации
           ↓
    Готовое расписание
           ↓
     Сохранение результата
           ↓
      Отправка email
```

## Дополнительные уточнения из обсуждения

- Основная цель — убрать ручное составление расписания повторяющихся задач.
- Пользователь сначала обсуждает крупную структуру продукта, затем бизнес-логику, затем архитектуру, API и implementation tasks.
- При конфликте пользователь должен принимать решение, а не алгоритм.
- Результат должен быть доступен в UI и отправляться на email.
- Хранить старые генерации как историю не планируется: нужен только последний успешный результат.
