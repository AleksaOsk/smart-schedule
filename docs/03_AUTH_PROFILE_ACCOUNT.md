# 42. Удаление аккаунта

Пользователь должен иметь возможность удалить свой аккаунт.

Перед удалением система должна запросить подтверждение.

Пользователю необходимо явно сообщить, что вместе с аккаунтом будут удалены связанные данные.

Пример:

```text
Вы уверены, что хотите удалить аккаунт?

Будут удалены:
- профиль;
- задачи;
- настройки рабочего расписания;
- текущее расписание;
- состояния генерации;
- другие связанные данные.

[Отмена]
[Удалить аккаунт]
```

После подтверждения отправляется запрос на удаление пользователя и связанных данных.

# 43. Персональные данные

На текущем этапе приложение хранит следующие персональные данные:

* email.

Email необходим для:

* регистрации / авторизации;
* идентификации пользователя;
* отправки готового расписания;
* связи с пользователем.

Имя и логин могут использоваться интерфейсом приложения, но не являются критически необходимыми персональными данными для основной бизнес-логики.

Пользовательские данные хранятся до тех пор, пока пользователь не удалит аккаунт, за исключением данных, для которых установлены отдельные сроки хранения.

При удалении аккаунта связанные пользовательские данные должны быть удалены.

# 44. Администрирование

Администратор системы должен иметь отдельные административные endpoints.

На текущем этапе администратору необходимо:

* найти пользователя;
* удалить пользователя по запросу;
* удалить связанные данные пользователя.

Административные endpoints не должны быть доступны обычным пользователям.

# 45. Безопасность

Безопасность является отдельной частью системы.

Для authentication планируется использовать механизм авторизации Supabase и предоставляемые им токены.

Backend должен проверять authentication и authorization для каждого защищённого запроса.

Основные требования:

* authentication;
* authorization;
* изоляция данных разных пользователей;
* безопасная работа с токенами Supabase;
* безопасное хранение секретов;
* защита API;
* валидация входных данных;
* защита административных endpoints;
* ограничение доступа к данным пользователя;
* защита базы данных;
* логирование важных security events;
* защита production-конфигурации.

# 46. Open Source

Исходный код проекта является открытым.

В репозитории не должны находиться:

* пароли;
* секретные ключи;
* database credentials;
* Supabase secret/service-role keys;
* email credentials;
* production environment variables;
* другие секреты инфраструктуры.

Секреты должны передаваться через environment variables или другой механизм безопасного хранения конфигурации.

## Дополнительные уточнения

- Email — основной необходимый персональный атрибут.
- Имя/логин не нужны для бизнес-логики.
- Admin нужен в первую очередь для удаления пользователя по запросу.
- Admin endpoints должны быть недоступны обычным пользователям.
- Секреты нельзя коммитить в open-source repository.
- Пользователь должен получить подтверждение перед необратимым удалением.
