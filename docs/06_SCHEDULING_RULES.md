# 13. Правила допустимого переноса задач

Для задачи определяется правило допустимого переноса.

Текущие варианты:

```java
NO(
    "no",
    "Нет"
)
```

`NO` означает, что задача не имеет ограничения на перенос относительно исходной даты.

Она может быть перенесена на ближайший подходящий день раньше или позже.

```java
DAY_BEFORE(
    "dayBefore",
    "Можно сдвинуть на день раньше"
)
```

Задача может быть выполнена только в рассчитанный день или на один день раньше.

```java
DAY_BEFORE_OR_AFTER(
    "dayBeforeOrAfter",
    "Можно сдвинуть на день раньше или позже"
)
```

Задача может быть выполнена в рассчитанный день, на один день раньше или на один день позже.

```java
DAY_TO_DAY(
    "dayToDay",
    "Обязательно день в день"
)
```

Задача должна быть выполнена именно в рассчитанный день.

> `NO`, `DAY_BEFORE`, `DAY_BEFORE_OR_AFTER` и `DAY_TO_DAY` являются не классическими приоритетами, а уровнями жёсткости ограничения даты. Однако эти уровни определяют порядок, в котором задачи первоначально распределяются генератором.

# 14. Порядок распределения задач

При первоначальном построении расписания задачи распределяются от наиболее жёстких ограничений к наиболее гибким:

```text
DAY_TO_DAY
    ↓
DAY_BEFORE
    ↓
DAY_BEFORE_OR_AFTER
    ↓
NO
```

Сначала размещаются задачи, которые имеют наименьшую возможность изменения даты.

После их размещения оставшееся доступное время используется для менее ограниченных задач.

# 15. Правила переноса `NO`

Для `NO` задача может переноситься на произвольное количество дней относительно рассчитанной даты.

При выборе места для такой задачи система рассматривает ближайшие доступные дни.

Предпочтительный порядок:

```text
1. ближайшая подходящая дата;
2. при равной дистанции сравнивается занятое время двух дней;
3. предпочтителен день с большей занятостью, если задача туда помещается;
4. если занятое время одинаково — предпочтителен день ДО исходной даты.
```

То есть, если задачу можно выполнить:

```text
на 2 дня раньше
или на 3 дня позже
```

выбирается вариант на 2 дня раньше.

Если существуют равноудалённые варианты, например:

```text
2 дня раньше
или
2 дня позже
```

и оба подходят, система сравнивает текущую занятость дней в часах.
Предпочитается более загруженный день, если задача в него помещается.
Если занятое время одинаковое, предпочтителен день ДО исходной даты.

# 16. Допустимое время выполнения

Задача может быть разрешена для выполнения:

* только днём;
* только ночью;
* днём или ночью.

Задача может занимать любое количество доступного времени в разрешённом интервале.

В течение одного дня может находиться любое количество задач, если их суммарная продолжительность и ограничения позволяют разместить их в доступном времени.

Например:

```text
09:00–10:00  Задача A
10:00–12:00  Задача B
12:00–12:30  Задача C
13:00–15:00  Задача D
...
```

Количество задач в одном дне не ограничивается фиксированным числом.

# 17. Дневные и ночные интервалы

При настройке рабочего расписания пользователь должен указать, есть ли у него ночные смены / ночные задачи.

Если ночной режим используется, пользователь задаёт обычный временной интервал.

Например:

```text
23:00 — 08:00
```

Таким образом, ночная смена может переходить через полночь.

Система должна учитывать, что один рабочий интервал может начинаться в одном календарном дне и заканчиваться в следующем.

## Дополнительные правила из последнего обсуждения

### DAY_TO_DAY conflict

Если несколько `DAY_TO_DAY` задач вызывают конфликт, пользователю показываются конфликтующие задачи. Система не выбирает одну сама.

### `NO`

При равноудалённых датах:

```text
left occupied = 5h
right occupied = 7h
task = 2h
→ prefer right
```

Если более загруженный день не вмещает задачу, рассматривается второй подходящий вариант.

Если занятость одинакова:

```text
→ prefer date before target
```

### `DAY_BEFORE_OR_AFTER`

Если `-1` и `+1` равноудалены и оба допустимы:

```text
→ prefer -1
```
