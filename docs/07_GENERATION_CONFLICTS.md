# 22. Генерация расписания

Генерация является основной бизнес-функцией SmartSchedule.

Генератор получает:

```text
Задачи
+
Подтверждённые даты последних выполнений
+
Рабочее расписание
+
Дневные / ночные интервалы
+
Правила допустимого переноса
+
Период генерации
+
Дополнительные настройки
```

и формирует:

```text
Сгенерированное расписание
```

---

---

# 23. Общий принцип работы генератора

Генерация должна начинаться с задач с наиболее жёсткими ограничениями:

```text
DAY_TO_DAY
    ↓
DAY_BEFORE
    ↓
DAY_BEFORE_OR_AFTER
    ↓
NO
```

На каждом этапе система проверяет:

* доступен ли нужный день;
* доступно ли необходимое количество времени;
* соответствует ли время суток требованиям задачи;
* не конфликтует ли задача с уже размещёнными задачами;
* разрешён ли перенос;
* не нарушаются ли другие ограничения.

Если задача не может быть размещена в соответствии с её ограничениями, возникает конфликт.

---

---

# 24. Конфликты

Конфликт возникает, если задача или несколько задач невозможно корректно разместить с учётом всех существующих ограничений.

Конфликт может возникнуть не только между двумя `DAY_TO_DAY` задачами.

Например:

```text
01.10
DAY_TO_DAY задача

02.10
DAY_TO_DAY задача
+
DAY_BEFORE задача

03.10
DAY_TO_DAY задача
```

Если задачи 02.10 не помещаются в доступное время, это может создать конфликт даже несмотря на то, что одна из задач допускает перенос.

Другой пример:

```text
Задача A:
DAY_TO_DAY
5 часов
только день

Задача B:
DAY_TO_DAY
3 часа
только ночь

Рабочий день:
день = 4 часа
ночь = 2 часа
```

Даже если суммарная длительность задач не превышает суммарное количество рабочего времени, задачи конфликтуют из-за несовместимости допустимых временных интервалов.

---

---

# 25. Конфликты не разрешаются автоматически

На текущем этапе система не должна самостоятельно принимать решение в ситуации, которую определила как конфликт.

При обнаружении первого неразрешимого конфликта генерация приостанавливается.

Пользователь получает возможность принять решение.

---

---

# 26. Состояния генерации

Генерация является отдельным процессом, состояние которого хранится в базе данных.

Предварительные состояния:

```text
STARTED
   ↓
GENERATING
   ↓
WAITING_FOR_USER
   ↓
GENERATING
   ↓
COMPLETED
```

При отмене:

```text
GENERATING / WAITING_FOR_USER
            ↓
        CANCELLED
```

Точный набор финальных статусов будет определён при проектировании модели генерации.

---

---

# 27. Хранение состояния генерации

Состояние текущей генерации хранится в базе данных.

Это необходимо для того, чтобы пользователь мог:

1. закрыть браузер;
2. снова открыть приложение;
3. запросить текущее состояние генерации;
4. получить информацию о конфликте;
5. продолжить генерацию.

Frontend не должен считать состояние генерации только локально.

После загрузки страницы frontend должен получить актуальное состояние с Backend.

---

---

# 28. Одновременные генерации

Для одного пользователя одновременно может существовать только одна активная генерация.

Если генерация находится в состоянии:

```text
STARTED
GENERATING
WAITING_FOR_USER
```

новая генерация не может быть запущена.

Пользователь должен сначала:

* продолжить текущую генерацию;
* либо отменить её / начать заново.

---

---

# 29. Ожидание решения пользователя

Генерация может находиться в состоянии:

```text
WAITING_FOR_USER
```

неограниченное время.

Она остаётся в этом состоянии до тех пор, пока пользователь:

* не предоставит решение;
* не отменит текущую генерацию;
* не начнёт новую генерацию после отмены текущей.

---

---

# 30. Разрешение конфликта

При обнаружении конфликта frontend получает информацию о конфликте и отображает модальное окно.

Пользователю показываются задачи, которые участвуют в конфликте. Пользователь выбирает, **какую именно задачу переносить**, и только затем выбирает дату/offset.

Варианты:

### Конкретная дата

Пользователь выбирает дату в календаре.

### Относительный перенос

Пользователь выбирает:

```text
-3 дня
-2 дня
-1 день
+1 день
+2 дня
+3 дня
```

Backend обязан проверить, допустимо ли выбранное пользователем решение.

---

---

# 31. Новый конфликт после решения пользователя

Решение пользователя может привести к новому конфликту.

Например:

```text
Пользователь перенёс задачу A
        ↓
A теперь конфликтует с B
        ↓
Backend обнаруживает новый конфликт
        ↓
WAITING_FOR_USER
        ↓
Frontend показывает новый конфликт
```

В этом случае пользователь снова должен выбрать решение.

Генерация продолжается до тех пор, пока все задачи не будут размещены либо пользователь не отменит генерацию.

---

---

# 32. Обработка нескольких конфликтов

Конфликты обрабатываются последовательно.

Как только генератор обнаруживает первый конфликт, он:

1. сохраняет состояние;
2. переводит генерацию в `WAITING_FOR_USER`;
3. передаёт информацию о конфликте frontend;
4. ожидает решения пользователя.

Следующий конфликт рассматривается только после продолжения генерации.

---

---

# 33. Отмена генерации

Пользователь может отменить текущую генерацию.

При отмене:

* текущая генерация прекращается;
* временные данные текущей генерации удаляются;
* промежуточное расписание удаляется;
* состояние генерации переводится в соответствующее финальное состояние.

Успешная предыдущая генерация пользователя при этом не должна быть затронута.

---

---

# 34. Начать генерацию заново

В интерфейсе конфликта должна быть возможность:

```text
[ Решить конфликт ]
[ Начать заново ]
```

### Решить конфликт

Пользователь выбирает решение, после чего текущая генерация продолжается.

### Начать заново

Текущая генерация отменяется.

Все промежуточные данные удаляются.

После этого пользователь может запустить новую генерацию с исходными настройками.

Предыдущая успешно завершённая генерация не должна удаляться из-за неудачной новой попытки.

---

---

# 35. Успешное завершение генерации

После того как все задачи успешно размещены:

```text
Generation
   ↓
COMPLETED
   ↓
Schedule
   ↓
Save
   ↓
Email
```

Завершённая генерация становится последней генерацией пользователя.

---

---

# 36. Хранение сгенерированного расписания

Хранится только последняя **успешно завершённая** генерация.

При создании новой успешной генерации:

```text
старое завершённое расписание
       ↓
удаляется

новое завершённое расписание
       ↓
сохраняется
```

Неуспешные и отменённые попытки генерации не должны заменять последнюю успешную генерацию.

---

---

# 37. Максимальный срок хранения расписания

Сгенерированное расписание хранится не более 2 месяцев.

Для автоматического удаления используется периодический backend-задачник.

Предварительная концепция:

```text
Ежедневный scheduler
        ↓
проверка сроков хранения
        ↓
найдены просроченные расписания
        ↓
удаление
```

## Дополнительные зафиксированные правила

### Конфликт DAY_TO_DAY

Если несколько `DAY_TO_DAY` задач не помещаются, система не должна сама выбирать задачу для переноса. Она показывает конфликтующие задачи и передаёт выбор пользователю.

### Разница между автоматическим placement и conflict resolution

Обычная допустимая постановка задачи выполняется автоматически.
Но если для выполнения нужно принять конфликтное бизнес-решение, решение принимает пользователь.

### Временный характер пользовательского переноса

Решение пользователя во время генерации относится к текущей генерации. Оно не должно незаметно менять постоянные настройки задачи (`lastExecutionDate`, recurrence, shift rule).

### Локальный жадный алгоритм

На MVP не требуется предварительно оптимально раскладывать все задачи по дням. Система работает последовательно и принимает локальные решения, в том числе для `NO`.
