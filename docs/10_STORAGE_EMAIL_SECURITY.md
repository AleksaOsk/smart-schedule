# 35. Успешное завершение генерации

После того как все задачи успешно размещены:

```text
Generation
   ↓
COMPLETED
   ↓
Schedule
   ↓
Save
   ↓
Email
```

Завершённая генерация становится последней генерацией пользователя.

---

---

# 36. Хранение сгенерированного расписания

Хранится только последняя **успешно завершённая** генерация.

При создании новой успешной генерации:

```text
старое завершённое расписание
       ↓
удаляется

новое завершённое расписание
       ↓
сохраняется
```

Неуспешные и отменённые попытки генерации не должны заменять последнюю успешную генерацию.

---

---

# 37. Максимальный срок хранения расписания

Сгенерированное расписание хранится не более 2 месяцев.

Для автоматического удаления используется периодический backend-задачник.

Предварительная концепция:

```text
Ежедневный scheduler
        ↓
проверка сроков хранения
        ↓
найдены просроченные расписания
        ↓
удаление
```

---

---

# 38. Email после генерации

После успешной генерации расписание отправляется пользователю на email.

Предполагаемые форматы:

* HTML;
* Excel.

HTML удобен для быстрого просмотра.

Excel позволяет пользователю при необходимости изменить расписание под себя после получения.

---

---

# 39. Асинхронная отправка email

Отправка email не должна блокировать основной процесс генерации.

Предполагается использование очереди сообщений, например:

* RabbitMQ;
* Kafka.

Концептуально:

```text
Generation COMPLETED
        ↓
создание события
        ↓
Message Broker
        ↓
Email consumer
        ↓
отправка email
```

При ошибке отправки должны выполняться повторные попытки.

Количество попыток, интервалы между попытками и окончательное состояние неуспешной отправки необходимо определить отдельно.

### OPEN QUESTION

Выбрать:

* RabbitMQ;
* Kafka;
* другой механизм.

Для pet-проекта также необходимо отдельно оценить, оправдано ли использование полноценного message broker на данном этапе.

---

---

# 40. Ошибка отправки email

Ошибка отправки email не должна отменять успешную генерацию расписания.

Например:

```text
Generation:
COMPLETED

Email:
FAILED
```

Расписание остаётся успешно сгенерированным и сохранённым.

Система должна иметь возможность повторить отправку.

### OPEN QUESTION

Необходимо определить:

* сколько попыток выполняется автоматически;
* через какие интервалы;
* сколько времени хранится информация о неудачной отправке;
* должен ли пользователь видеть статус отправки;
* должна ли существовать кнопка «Отправить ещё раз».

---

---

# 41. Изменение данных после генерации

Изменение исходных данных пользователя не должно автоматически изменять уже созданное расписание.

Например:

```text
Пользователь изменил длительность задачи
        ↓
существующее расписание не изменяется
```

Чтобы получить расписание на основании новых данных, пользователь запускает новую генерацию.

При этом последняя успешная генерация должна сохраняться до тех пор, пока новая генерация не завершится успешно.

# 47. Database

Основная база данных:

**PostgreSQL**.

Supabase используется как инфраструктура для PostgreSQL и authentication.

MongoDB на текущем этапе не используется.

## Дополнительные решения

- Email failure не меняет `Generation = COMPLETED`.
- Для Excel пользователь получает возможность дальше редактировать расписание вручную.
- Старый schedule удаляется только после успешного создания нового, а не при старте новой генерации.

- Manual resend.

- Точная «2 months» policy.

- Полная Supabase RLS model.
