# 50. Нефункциональные требования

Система должна:

* корректно разделять данные разных пользователей;
* не раскрывать данные одного пользователя другому;
* валидировать входные данные;
* корректно обрабатывать ошибки;
* не хранить секреты в Git;
* иметь автоматические тесты критической бизнес-логики;
* иметь тесты генератора расписания;
* корректно восстанавливаться после ошибок генерации;
* не изменять постоянные данные пользователя при незавершённой генерации;
* позволять восстановить состояние `WAITING_FOR_USER` после повторного входа;
* не допускать одновременной генерации двух расписаний для одного пользователя.

# 51. Тестирование генератора

Генератор является критической частью приложения и должен иметь отдельное покрытие тестами.

Минимально необходимо тестировать:

### Расчёт следующей даты

```text
lastExecutionDate
+
recurrence
→
nextExecutionDate
```

### Пропущенные периоды

```text
последнее выполнение
→ несколько периодов пропущено
→ периодичность последовательно прибавляется
→ актуальная дата найдена
```

### Дата за пределами целевого месяца

```text
следующая дата
>
последний день целевого месяца
→
задача не добавляется
```

### Простая генерация

```text
1 задача
→ задача помещается
→ расписание создано
```

### Приоритет распределения

```text
DAY_TO_DAY
→ DAY_BEFORE
→ DAY_BEFORE_OR_AFTER
→ NO
```

### Недостаток времени

```text
доступно 8 часов
задачи = 9 часов
→ конфликт
```

### Конфликт по времени суток

```text
задачи помещаются по общей продолжительности
НО
одна требует день
другая требует ночь
и доступного времени соответствующего типа недостаточно
→ конфликт
```

### DAY_TO_DAY

```text
DAY_TO_DAY
→ задача не может быть автоматически перенесена
→ конфликт
```

### DAY_BEFORE

```text
DAY_BEFORE
→ задача может использовать рассчитанный день
или день раньше
```

### DAY_BEFORE_OR_AFTER

```text
DAY_BEFORE_OR_AFTER
→ задача может использовать рассчитанный день
или день раньше / позже
```

### NO

```text
NO
→ задача может переноситься без ограничения
→ предпочтение ближайшему подходящему дню раньше
→ при равном расстоянии учитывается общая загрузка
```

### Разрешение конфликта пользователем

```text
CONFLICT
→ WAITING_FOR_USER
→ user decision
→ GENERATING
→ COMPLETED
```

### Новый конфликт после решения

```text
CONFLICT A
→ user decision
→ CONFLICT B
→ WAITING_FOR_USER
→ user decision
→ ...
```

### Начало генерации заново

```text
CONFLICT
→ START_OVER
→ временные данные удалены
→ новая генерация
```

### Отмена генерации

```text
WAITING_FOR_USER
→ CANCELLED
→ временные данные удалены
→ последняя успешная генерация не затронута
```

## Дополнительные обязательные edge cases

- `NO`: равноудалённые даты, разная occupied hours.
- `NO`: более загруженный день не вмещает задачу.
- `NO`: одинаковая occupied hours → день раньше.
- `DAY_BEFORE`: нельзя `target + 1`.
- `DAY_BEFORE_OR_AFTER`: `-1` предпочтительнее `+1` при равной дистанции.
- `DAY_AND_NIGHT`: не требует двух смен одновременно.
- Конфликт нескольких `DAY_TO_DAY`: пользователь выбирает task.
- User resolution может создавать новый conflict.
- Active generation uniqueness.
- User A → User B data denied.
- Email failure не меняет generation result.
